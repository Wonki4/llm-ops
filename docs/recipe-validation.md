# 레시피 검증과 자동 공개

`벤치마크 → 레시피 검증`은 기존 개별 측정을 묶는 관리자 작업이다. 레시피 목록의 다중 선택과 서빙 홈의 현재 클러스터·네임스페이스에서 시작한다. 일반 성능·캐시·정확도 측정 기록과 기존 배포·레시피·카탈로그·라우팅 화면을 재사용한다.

## 실행과 권한

1. 관리자가 후보 순서, 대상 클러스터·네임스페이스, GPU 상한, 부하와 품질 하한, 선정 지표, 단계별 제한, 공개할 Ingress 호스트와 LiteLLM 호출명을 고정한다.
2. 후보별 CPU Job이 실제 서빙 이미지와 스토리지에서 가중치 전체 샤드, 토크나이저, 실행 의존성을 검사한다. 정확도 평가를 선택하면 별도 평가 이미지·데이터셋도 검사한다. 파일을 해싱하므로 대형 모델에서는 자산 점검 한도를 충분히 준다.
3. 후보 하나씩 GPU를 할당한다. 각 풀의 GPU 수용량이 있는 노드를 먼저 찾고, 파일을 검사한 노드에서 기동·측정한다. 단일 노드 다중 GPU와 별도 prefill/decode 풀을 지원한다. 각 풀의 복제본은 검사한 노드에 배치하므로 해당 노드에 풀 전체 GPU가 들어가야 한다. 다중 노드 tensor/pipeline sharding은 지원하지 않는다.
4. 기동 확인과 예열을 제외하고 일반 성능은 기본 3회 실행한다. 설정한 캐시·표준 정확도 평가를 추가한다. 모든 필수 측정이 성공해야 합격하며 누락·부분 실패·비정상 수치는 탈락이다.
5. 로그·이벤트·실제 설정을 저장하고 후보 리소스를 제거한다. 종료 중인 GPU Pod와 라우터 Application까지 사라져야 다음 후보로 넘어간다.
6. 합격 후보의 반복 중앙값으로 서버가 순위를 정한다. 선정 후보를 복원하고 이미지·파일·데이터셋을 대조한 뒤 필수 측정을 다시 실행한다. 복원 실패 시 다음 합격 후보를 검증한다.
7. 최종 검증을 통과한 후보만 Ingress와 LiteLLM에 공개한다. 기존 Ingress 경로와 충돌하면 중단한다. 작업 고유의 LiteLLM 모델 ID로 실제 응답을 확인하고 기존 카탈로그를 이용한다. 다른 배포의 동일 호출명 등록을 교체하지 않는다.

포털 관리자만 시작·취소·수정 후보 추가·LLM 분석 기록을 할 수 있다. 공개는 팀·키·모델 접근그룹 권한을 새로 부여하지 않는다. 기존 LiteLLM 정책이 적용되며, 같은 호출명을 이미 허용받은 키에는 새 등록도 같은 정책이 적용된다.

GPU 상한과 순차 실행은 **작업 단위**다. 서로 다른 검증 작업 사이의 전역 GPU 예약은 하지 않으며 클러스터 스케줄러와 quota가 최종 배치를 결정한다. 취소나 시간 초과 후에도 정리에 실패하면 정리 상태를 유지하고 재시도한다.

## 측정과 선정의 의미

- `output_throughput`: 같은 GPU 수와 같은 서버 토크나이저의 출력 tok/s를 비교한다.
- `throughput_per_gpu`: 출력 tok/s를 후보 GPU 수로 나눈다. 서버 토크나이저가 같아야 한다.
- `request_throughput`, `p99_ttft_ms`: 서로 다른 토크나이저/양자화 후보에 사용할 수 있다. 공통 입력 생성용 토크나이저를 지정할 수 있으며 그 버전도 검사한다. 서버의 실제 토큰 사용량을 결과에 보존한다.
- 서로 다른 가중치에는 실행 전에 표준 평가 task/metric의 절대 품질 하한을 지정해야 한다. 평가 결과가 없으면 합격하지 않는다.
- prefix 캐시 비교는 단일 vLLM Pod에서만 지원한다. P/D나 SGLang 후보와 함께 선택하면 시작 전에 사유를 반환한다. 준비 요청을 제외한 토큰 카운터 증가량을 사용하며 `0%`와 `측정 불가`를 구분한다.
- 일반 성능 반복마다 seed를 바꾸고 별도 입력으로 예열한다. 측정 간 캐시를 강제로 초기화하지는 않는다. 전용 캐시 비교의 두 구간과 일반 반복 측정은 결과를 구분해서 읽는다.

가중치/이미지/토크나이저 해시는 기동 전과 최종 복원 시 비교한다. 서빙 및 라우터 컨테이너의 실제 image ID도 비교한다. 레지스트리 태그나 Helm chart 내용을 실행 중 덮어쓰지 말고 digest 및 변경 불가능한 chart 버전을 사용한다. 변경을 발견하면 공개하지 않는다. 실행 중 파일을 외부에서 수정하는 것을 차단하는 스토리지 잠금은 제공하지 않으므로 검증 자산은 읽기 전용 버전 디렉터리로 제공한다.

## 실패 수정과 LLM/MCP

등록 레시피 비교에서는 전 후보가 탈락하면 `관리자 입력 대기`가 된다. 상세의 진단 패널에 시도별 이벤트·현재/직전 로그·LLM 설명·수정안을 표시한다. `수정 후보 추가`는 기존 레시피 폼과 YAML 차이를 사용한다. 확인한 내용은 새로운 후보 스냅샷이며 공유 레시피는 바뀌지 않는다. 부하·품질 기준 변경은 새 작업으로 시작한다. 원래 작업의 전체 시간 한도는 후보를 추가해도 초기화하지 않는다.

MCP 도구는 화면과 같은 API 함수를 호출한다.

| MCP 도구 | 역할 |
|---|---|
| `preview_recipe_validation` | 클러스터·GPU·스토리지 설정을 검토 |
| `start_recipe_validation` | `ValidationCreate`로 작업 시작 |
| `list_recipe_validations`, `get_recipe_validation` | 진행·시도·진단·측정 조회 |
| `cancel_recipe_validation` | 진단 보존 후 리소스 정리 요청 |
| `explain_recipe_validation_attempt` | LLM 설명과 레시피 patch 기록 |
| `add_recipe_validation_candidate` | 대기 작업에 초안 또는 수정 후보 추가 후 재개 |
| `get_recipe_search_guide` | MCP 탐색 스킬과 최신 생성/후보/레시피 스키마 |
| `get_recipe_search_context` | 간결한 이력, 현재 최선, 남은 한도, 다음 동작 |
| `preview_recipe_validation_candidate` | 초안/patch의 GPU·스토리지·차이 확인 |
| `finish_recipe_search` | 탐색 종료 후 서버 선정·최종 재검증 시작 |

LLM은 기존 관리자 MCP 클라이언트에서 진단을 읽고 수정안을 제안한다. 포털 서버가 별도 LLM을 호출하거나 임의로 가중치를 교체하지 않는다. 관리자가 승인한 탐색 범위 안의 후보는 MCP 클라이언트가 반복 제출한다. 범위를 넓히는 변경은 새 작업으로 분리한다. MCP 재호출 시 같은 `request_key`를 유지한다. 사용자+키가 같은 생성 요청, 작업+키가 같은 후보 추가는 기존 기록을 반환하며 다른 내용으로 재사용하면 409다.

## 레시피 자동 생성과 반복 최적화

`새 검증 작업 → MCP 자동 탐색`에서 모델과 조건만 지정한다. 레시피 선택 없이 만들 수 있다.
작업 상세의 `MCP 실행 요청 복사`를 연결된 Claude Code/Codex에 전달한다. 포털이 클라이언트를
자동 실행하지는 않는다. MCP에서 직접 시작한 작업도 같은 화면에 나온다.

클라이언트는 `get_recipe_search_guide`로 서버와 함께 배포된
[탐색 스킬](../backend/app/mcp/skills/optimize-serving-recipe/SKILL.md)을 읽는다.
별도 개인 스킬 설치 없이 MCP 도구로 읽을 수 있으며, 로컬 스킬로 배포할 때는 이 디렉터리를 복사한다.
첫 레시피 초안을 작성하고 CPU 자산 점검·기동·측정 결과를 바탕으로 실패를 고치거나 성공한 후보를 더 개선한다.
포털 내부 LLM 호출이나 LLM API 키는 추가하지 않는다.

- `conditions.search`는 대상 모델, 허용 대체 모델, 최대 후보 수, 탐색 시간,
  개선 정체 후보 수, 유의미한 개선 비율, 최소 컨텍스트를 고정한다.
  기본값은 12개 / 6시간 / 3개 / 1% / 4096토큰이다. 전체 작업 시간에는 복원·최종 검증 시간을 추가로 남긴다.
- `candidates: []`로 시작하면 첫 초안을 기다린다. 초안은 `CandidateAdd.recipe`, 개선은
  `source_candidate_id`와 `patch`로 제출한다. `hypothesis`에는 변경 의도를 기록한다.
- 각 후보 정리 후 합격 여부와 무관하게 `awaiting_planner`에서 다음 제안을 받는다.
  처음 합격했다고 바로 공개하지 않는다. 호출이 끊겨도 진행 중인 측정과 정리는 워커가 계속한다.
- 제출 시 `expected_candidate_count`가 현재 이력과 같아야 한다. 작업 행 잠금과 요청 키가
  동시 클라이언트의 중복 제출을 막는다. 이름만 바꾼 같은 설정도 재실행하지 않는다.
- 공통 부하·품질·시간·GPU 범위를 수정할 수 없다. 모델 정체성은 선언한 HF 저장소 또는 로컬 경로이며,
  CPU 점검에서 실제 파일 해시를 저장한다. 서로 다른 파일을 비교하려면 품질 하한이 필요하다.
  최소 컨텍스트와 측정 입력+출력 길이를 충족하는 명시적 엔진 설정이 필요하다.
- 후보 수/시간 한도 또는 성공 후보 이후 개선 정체 기준을 만족하면 서버가 탐색을 닫는다.
  여러 작은 개선은 마지막 유의미한 최고점 대비 누적한다. 중지 기준과 관계없이 실제 합격 최고 중앙값을 선정한다.
  탐색 시간 초과 시 진행 중 비교를 정리하고 완료된 최선 후보를 사용한다. 전체 시간 초과는 작업을 종료한다.
- 클라이언트는 더 시도할 근거가 없으면 `finish_recipe_search`로 일찍 종료할 수 있다.
  최종 재검증에 실패하면 다음 합격 후보로 넘어간다. 합격 후보가 없으면 근거를 보존하고 실패로 종료한다.
- 최종 공개 성공 시 복원한 이미지/리비전 설정을 반영한 새 레시피를 한 번 저장한다.
  중간 초안은 후보 스냅샷에만 보존하며 원본 공유 레시피를 덮어쓰지 않는다.

이 기능이 찾는 것은 고정된 조건과 한도 안에서 **측정한 최선 후보**다. 전역 최적해나 지연 개선을 보장하지 않는다.

## 폐쇄망 준비

- 서빙 이미지에 `python`, `transformers`, `huggingface_hub`, `aiohttp`를 포함한다. prefix 측정은 vLLM의 tokenize/completions/metrics 경로와 `prometheus_client`가 필요하다.
- 정확도 이미지는 기존 `bench/Dockerfile`의 포털 러너와 `lm-eval/0.4.4` 표준 채점을 사용한다. 같은 경로의 모델 토크나이저와 평가 데이터셋을 미리 준비한다. 실행 시 패키지를 설치하지 않는다.
- 모델 가중치의 모든 shard/index/config/tokenizer/필요한 remote-code 파일과 평가 데이터셋 캐시를 배포와 러너에서 읽을 수 있게 스토리지 바인딩한다. HF 토큰 같은 값은 이미지에 넣지 않는다.
- `airgap=true`는 `HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `HF_DATASETS_OFFLINE`을 강제한다. 외부 통신 자체의 차단은 클러스터 NetworkPolicy/방화벽에서 적용한다.
- P/D에서는 sidecar, EPP, Envoy 이미지와 Helm chart도 내부 저장소로 옮긴다. ArgoCD는 선택한 대상 클러스터에 적용할 수 있어야 한다.
- 백엔드 서비스 계정에 Nodes 조회, 대상 Deployment/Service/Job/Pod/Secret 관리, 로그·이벤트 조회, 공개 시 클러스터 Ingress 충돌 조회가 필요하다. 라우터는 기존 ArgoCD Application 권한도 필요하다.

## 저장과 운영

마이그레이션 `064_recipe_validation`은 작업·후보·시도 3개 테이블과 배포·벤치마크 연결 필드, 라우터 비공개 상태를 추가한다. `065_recipe_search`는 선택적인 탐색 종료 상태를 추가한다. 기존 기록은 그대로 열린다. API와 워커를 배포하기 전에 마이그레이션한다.

```sh
cd backend
python -m alembic upgrade head
python -m app.worker
```

측정 결과는 기존 벤치마크 행에 한 번 저장하고 상위 작업은 ID와 집계만 참조한다. 검증용 배포의 수정·재적용·삭제, 검증 측정의 별도 취소/삭제는 상위 작업과 충돌하지 않도록 막는다. 공개된 배포는 일반 배포로 관리할 수 있다. 실패 후보의 배포 행은 `retired` 상태로 보존된다.

워커는 DB 행 잠금으로 전이를 직렬화하며 리소스 ID를 먼저 저장한다. 재시작하면 동일 ID의 Job/Deployment/등록을 이어간다. 실행 중 측정 Job이 외부에서 삭제되면 새 측정을 자동 생성하지 않고 실패로 기록한다. 모든 Job 인증 값은 소유자 참조가 있는 Secret으로 전달한다. 원본 후보 스냅샷은 암호화하고 API 및 진단에서는 비밀 값을 가린다.

## 로컬 검사와 사내 인수

```sh
cd backend
python -m pytest -q tests/test_recipe_validations.py
# 선택: 마이그레이션을 적용한 독립 PostgreSQL DB에서 동일 테스트
# DB 이름은 반드시 recipe_validation_test. URL에 있는 인증 값은 기록하지 않는다.
VALIDATION_TEST_DATABASE_URL="$TEST_DATABASE_URL" python -m pytest -q tests/test_recipe_validations.py
cd ../frontend
npm exec tsc -- --noEmit --incremental false
```

로컬에서는 실제 SQL 기록과 제어 가능한 외부 런타임으로 실패→정리→다음 후보→복원→재검증→공개 전이를 검증한다. 브라우저 시뮬레이션 결과의 성능 수치는 실제 GPU 성능을 뜻하지 않는다.

사내 인수에서는 다음을 실제 자산으로 확인한다.

### 이번 로컬 확인 결과

- 관련 백엔드 회귀 테스트 229개 통과. 신규 기능 27개는 SQLite 전이·런타임 어댑터 검사에 포함된다.
- PostgreSQL 통합 검사 26개 통과. 신규 마이그레이션 064 롤백·재적용 통과.
- TypeScript 및 변경 프런트엔드 ESLint 검사 통과.
- 브라우저: 다중 후보 전달, B 클러스터/serving-b 선택, 새로고침 후 상태 유지, 실패 진단, 수정 폼/YAML 차이/후보 추가 후 재개, 선정/최종 재검증, 기존 개별 측정 비교 화면 연결을 확인했다. 실행 수치는 격리 시뮬레이터에서 생성했다.
- 전체 백엔드 실행에서는 변경 전 코드에서도 재현되는 팀·키 관련 테스트 실패 18개와 실서비스 연결이 필요한 예산 E2E 실패/오류가 남는다. 이번 변경과 관련된 기존 측정 삭제 테스트 fixture는 신규 nullable 연결 필드에 맞게 보완했다.

### MCP 자동 탐색 확장 확인

- 관련 백엔드 회귀 테스트 211개, 그중 검증/탐색 기능 테스트 35개 통과.
- 동일 기능 테스트 35개를 독립 PostgreSQL에서도 통과. `065_recipe_search` 적용·롤백·재적용 통과.
